# Scribase Mail Studio — competitive & GTM strategy

Scope note: `PLAN-2026-10-23-DEEP.md` (pages/APIs/features) does not exist yet in
this repo as of this writing. This file covers competitive positioning, ICP/user
research and journey mapping, and growth moves only — not feature/page specs.

Current product reality (from `README.md`, `package.json`, `GROWTH-BLOCKERS-2026-10-18.md`):
a fork of useSend, AGPL-3.0, self-host via `./scripts/selfhost.sh` or use
`mail.scribase.com` hosted. Core differentiator already shipped: drop-in
`resend` npm SDK compatibility via `RESEND_BASE_URL`/`baseUrl`, Svix-signed
webhooks, inbound email, SMTP/Oracle Cloud sending providers, deliverability
controls (warm-up caps, reputation auto-pause, content screening, review
queue). Live pricing (confirmed in GROWTH-BLOCKERS audit): Free $0/3,000
emails, Pro $20/mo/50,000, Scale $90/mo/100,000, $0.90/1,000 overage.

## 1. Direct competitors

- **Resend** (closed source, hosted only)
  - Pricing: Free 3,000/mo (100/day cap, 3 domains); Pro $20/mo for 50,000
    (or $35/mo for 100,000); Scale $90/mo for 100,000 up to $1,150/mo for
    2.5M; overage $0.90/1,000 (down to ~$0.46-0.52/1,000 at top Scale tiers);
    Enterprise custom past 3M/mo. Separate contact-based Broadcasts pricing
    from $40/mo for 5,000 contacts.
  - Strongest feature: the SDK and DX itself — the `resend` npm/Python/Go
    SDKs are the de facto standard devs reach for first; best-in-class docs
    and React Email integration.
  - Weakest point: no self-host option at all. Closed source. Every email,
    contact and webhook payload lives on Resend's infra with no audit path —
    a hard no for regulated or data-residency-sensitive teams, and a billing
    dependency that scales forever with volume.

- **Postmark** (closed source, hosted only)
  - Pricing: Free 100 emails/mo forever (dev/test only, no overage allowed).
    Paid at 10,000/mo: Basic $15/mo, Pro $16.50/mo (365-day retention +
    inbound + 10 domains), Platform $18/mo (unlimited domains/seats).
    Overage $1.80/$1.30/$1.20 per 1,000 respectively. ~$105/mo at 100,000,
    ~$850/mo at 1M.
  - Strongest feature: deliverability reputation — oldest, most trusted
    dedicated-transactional-only sending reputation in the market; message
    streams separate transactional from broadcast IP reputation out of the box.
  - Weakest point: no self-host, no AGPL/OSS option, and per-email cost is
    2-6x Resend/Scribase at volume (e.g. ~$850/mo at 1M vs Resend's Scale
    ladder). No `resend` SDK compatibility — switching requires a real
    code migration, not an env var.

- **useSend** (the upstream project Scribase Mail Studio is forked from —
  now a direct competitor since both are live, separately branded products)
  - Pricing: hosted cloud "Paid" plan at $10/mo minimum usage credit, then
    $0.0004/transactional email and $0.001/marketing email (effectively
    ~$0.40-$1.00 per 1,000, cheaper than Resend at raw email cost). Free
    tier 3,000/mo, 100/day cap, 1 contact book, 1 domain. Self-host is free
    but requires bringing your own AWS SES account, so true all-in cost
    includes SES charges + ops time.
  - Strongest feature: thin wrapper over SES means lowest raw per-email
    cost of any option here if you're comfortable managing an AWS SES
    account and sending reputation yourself.
  - Weakest point: **no Resend SDK compatibility** — its API is its own
    shape, so there is no drop-in migration path from Resend, only a real
    integration rewrite. No bundled SMTP/Oracle provider option — SES is
    mandatory. No inbound email. This is Scribase Mail Studio's single
    most important competitor to beat because it is the same codebase
    lineage with a materially weaker migration story.

- **FreeResend** (MIT, closed-feature-set open source)
  - Pricing: free to self-host, no license fee; running cost is whatever
    Amazon SES charges (~$0.10/1,000 emails).
  - Strongest feature: also claims drop-in Resend compatibility via
    `RESEND_BASE_URL`, same positioning angle as Scribase Mail Studio, and
    is MIT (more permissive than AGPL) which some companies prefer for
    internal forks.
  - Weakest point: small project (a few hundred stars, short commit
    history per public reporting), no campaigns/contacts/audiences/
    templates/broadcast UI, no inbound email, mandatory AWS SES (so same
    "bring your own SES account" friction as useSend), no hosted/managed
    option at all — self-host or nothing.

- **Postal** (MIT, self-hosted mail server, not an ESP frontend)
  - Pricing: free software; real infra cost is the user's own (app server
    + MariaDB + RabbitMQ, realistically $60-120/mo in managed infra, plus a
    static IPv4 with working reverse DNS and unblocked port 25).
  - Strongest feature: full MTA with IP pool management, multi-tenant
    org/domain isolation, and built-in spam engine integration (SpamAssassin/
    Rspamd/ClamAV) — more infrastructure depth than any ESP-style competitor
    here; good fit for agencies running mail for many clients.
  - Weakest point: no Resend-compatible or Resend-shaped API at all (its own
    REST/SMTP shape), no hosted option, and the operational burden (4GB+ RAM,
    RabbitMQ, MariaDB, port 25 access, DKIM/reputation entirely self-managed)
    is the highest of any competitor listed — not a realistic choice for a
    solo founder who wants to ship email in an afternoon.

## 2. Differentiation plan — beat each one on a named axis

- **vs Resend — self-host + source-visible axis, keep SDK parity as table
  stakes.** Resend cannot be self-hosted at any price; Scribase Mail Studio's
  one-command `./scripts/selfhost.sh` plus the fact that `baseUrl` is the
  *entire* migration (zero SDK/API rewrite) is the whole pitch. Concrete
  move: ship a side-by-side "same curl request, same response shape" diff
  snippet in docs (not just prose) showing `resend.emails.send()` output is
  byte-identical field-for-field — this is more convincing than a feature
  table and is cheap to produce from the existing Resend-compat test suite.

- **vs Postmark — price-at-volume + migration cost, concede nothing on
  deliverability messaging.** At 100,000 emails/mo Postmark is ~$105/mo;
  Scribase Mail Studio hosted Scale is $90/mo for the same volume with the
  option to self-host for infra cost only. Concrete move: publish a
  volume-ladder comparison table (10k/50k/100k/500k/1M) with sources dated,
  the same format GROWTH-BLOCKERS already validated for the README table —
  extend that exact table to include Postmark's published ladder so the
  price gap is explicit at every tier, not just one data point.

- **vs useSend (the direct fork-sibling) — the Resend-SDK-compatibility
  gap is the single biggest wedge available.** useSend's own public
  positioning (per openalternative.co listing) explicitly does not claim
  Resend API compatibility — its API is its own shape. Concrete move: a
  dedicated "Migrating from useSend" doc page is lower priority than a
  direct comparison row added to the existing README/marketing comparison
  table (which currently lists Resend/useSend/Postal but should make the
  "works with the `resend` SDK via baseUrl: Yes / No" row impossible to
  miss — it already exists in the table, so the move here is paid-search
  and content targeting the exact phrase "useSend resend compatible" and
  "useSend alternative" where today zero content exists pointing searchers
  from useSend's own docs/GitHub issues toward Scribase Mail Studio).

- **vs FreeResend — same positioning angle, win on completeness and
  managed option.** FreeResend matches the drop-in-compatibility pitch but
  has no campaigns, contacts, audiences, templates, broadcast editor, or
  inbound email, and mandates AWS SES with no hosted alternative. Concrete
  move: a direct "FreeResend vs Scribase Mail Studio" feature-parity table
  (campaigns: yes/no, inbound: yes/no, hosted option: yes/no, SES
  requirement: yes/no) targeting anyone who found FreeResend first via
  GitHub search — since FreeResend's own README is where that comparison
  keyword traffic already exists, a GitHub repo README/wiki link or issue
  comment pointing to the comparison is the lowest-cost placement.

- **vs Postal — ease-of-operation axis.** Postal demands a static IPv4
  with working rDNS, unblocked port 25, RabbitMQ, MariaDB and 4GB+ RAM
  minimum. Concrete move: the existing `./scripts/selfhost.sh` one-command
  Docker Compose flow (already shipped per README) plus the ability to
  send through *any* SMTP relay (not a mandatory MTA you operate yourself)
  is the pitch — make "bring your own SMTP relay, skip the MTA" an explicit
  headline in any Postal-adjacent content (r/selfhosted, HN) rather than a
  buried README bullet, since that is the exact operational pain Postal
  threads on that subreddit describe.

## 3. Primary user persona / ICP

- **Primary: solo/small-team SaaS founder or indie developer already
  using (or about to adopt) the `resend` npm SDK**, running a Next.js/
  Node/Python backend, who self-hosts the rest of their stack on
  Supabase/Neon/Postgres+Redis and wants email to follow the same
  "own your infra" pattern rather than add another metered SaaS bill.
  Job-to-be-done: "send transactional email (signup confirmations,
  password resets, receipts) reliably without writing SMTP/DKIM code
  myself, and without a line item that scales linearly with my user
  growth forever."
  - Trigger moment: Resend's free tier's 100/day cap is hit, or a Pro/Scale
    invoice lands and the founder searches "Resend self-hosted alternative"
    or "Resend too expensive" — this exact phrase pattern is visible in the
    competitor-comparison article titles found during research (toolradar,
    usecarly, coldletter all publish "Resend alternatives" content, meaning
    the search demand is real and already being served by third parties,
    not Scribase).

- **Secondary: agencies/platforms sending email on behalf of multiple
  client projects** (the Postal "multi-tenant" use case) who want the
  Resend SDK shape (for their own devs' familiarity) without Postal's MTA
  operational burden.

## 4. User journey map — discovery to paying/retained

1. **Discovery** — hits a "Resend alternative" / "Resend pricing too high"
   / "self-hosted Resend" search, or finds the GitHub repo via
   openalternative.co-style directories, or reads the comparison table on
   `scribase.com/mail`.
2. **Evaluation** — reads the README/marketing comparison table; checks the
   "works with resend SDK via baseUrl" claim specifically, since that is the
   one fact that determines migration cost before any signup.
3. **First try** — either (a) hosted: signs up free at `mail.scribase.com`,
   or (b) self-host: runs `git clone ... && ./scripts/selfhost.sh`.
4. **Activation moment** — sends the first test email through the `resend`
   SDK pointed at the new `baseUrl` and sees it land (Mailpit locally, or
   real inbox when hosted). **This is the single biggest drop-off risk
   step** — GROWTH-BLOCKERS-2026-10-18.md documents that this exact test
   send was silently held by the first-sends review gate with a `200` OK
   response and no visible signal, so a brand-new evaluator's very first
   "does this even work" test looked like silent failure. That specific
   bug is marked fixed and deployed in that file, but the step remains the
   highest-risk point in the journey structurally (any future gate, queue
   delay, or DNS/DKIM misconfiguration during self-host produces the same
   "I sent it and nothing happened, is this broken or is it me" moment) —
   any product change touching the send pipeline should get a synthetic
   send-and-confirm smoke test before shipping, specifically because this
   step has already caused one silent-failure incident.
5. **Domain + DKIM setup** — adds a real sending domain, copies DNS records
   shown in-dashboard; drop-off risk here is secondary (self-inflicted DNS
   propagation delay is expected and self-explained by the product).
6. **Switch production traffic** — replaces the real `RESEND_BASE_URL`/
   SDK init in their app; because this requires no further code change,
   this step has near-zero abandonment once step 4 has succeeded.
7. **Paying/retained** — free tier is hit (3,000/mo or 100/day), or the
   team wants Pro features (lifted daily cap, more domains/webhooks);
   converts to Pro $20/mo or stays self-hosted indefinitely on
   infrastructure cost alone (self-host is a valid "retained but non-
   paying" outcome by design — monetization for that segment has to come
   from support/managed-upgrade upsell, not from gating the self-host path).

## 5. Three concrete growth moves

1. **Target the exact long-tail keyword gap third-party sites are already
   capturing: "useSend resend compatible" / "useSend vs Resend API" /
   "FreeResend vs [alternative]".** Today those exact comparison searches
   are answered by openalternative.co, emailbump.com and similar
   aggregator sites, not by Scribase Mail Studio's own site — meaning the
   demand is proven (multiple independent sites have written comparison
   content around exactly this niche) but Scribase isn't capturing it.
   Action: extend the existing README/marketing comparison table (which
   already has the right columns: self-host, resend SDK compat, pricing)
   to explicitly include FreeResend as a row, since it is the one
   competitor making the identical "drop-in Resend replacement" claim and
   currently has zero comparison content pointing at Scribase.

2. **File/comment on the specific GitHub issues where Resend users are
   already asking for self-hosting.** Resend being closed-source with no
   self-host option is a known, recurring complaint pattern in developer
   communities (visible in the volume of third-party "Resend alternatives"
   content found during this research — 7+ independent articles exist on
   this exact topic). Action: identify and respond helpfully (not spammy)
   in public GitHub discussions/issues on projects that integrate the
   `resend` SDK where users mention wanting self-hosting or cost concerns,
   linking the Resend-compat migration guide, not a sales pitch — this is
   a zero-cost, zero-ad-spend channel directly matching where the ICP
   already congregates (GitHub, not social).

3. **Ship the FreeResend-style completeness comparison as a dedicated page
   and submit it to the same open-source directories already listing
   useSend and FreeResend** (openalternative.co/alternatives/resend lists
   10+ Resend alternatives including useSend already; Scribase Mail Studio
   should have its own listing there with the same positioning columns).
   Action: submit Scribase Mail Studio to openalternative.co's Resend
   alternatives page and any directory already carrying useSend/FreeResend/
   Postal, since those pages are confirmed to exist, confirmed to rank for
   the exact "Resend alternative" query, and currently do not list Scribase
   Mail Studio — this is the lowest-effort, proven-demand channel of the
   three.
