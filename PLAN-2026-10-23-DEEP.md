## APIs (apps/web/src/app/api)

- `GET/POST /api/auth/[...nextauth]` — NextAuth session/callback handlers.
- `POST /api/dev/email-preview` — body `{ html | templateId, variables }` ->
  `{ html }`. Dev/internal only.
- `GET /api/health` -> `{ data: "Healthy" }`.
- `POST /api/internal/inbound` — internal-secret header required. Body:
  `InboundMailInput` (recipientDomain, from, to[], cc[], bcc[], replyTo[],
  subject, text?, html?, headers?, rawStorageKey?, sizeBytes, spf/dkim/
  dmarcResult?, spamScore?, attachments[]) -> `{ id }`. Called by
  `apps/smtp-server`.
- `GET /api/internal/inbound/domains` — internal-secret header -> list of
  `{ id, name }` for domains with `receivingEnabled`.
- `ALL /api/resend/[[...route]]` — Resend-compat public API, API-key bearer
  auth. Includes `GET /emails/received`, `GET /emails/received/:id`,
  `GET /emails/received/:id/attachments[/:aid]`, `POST
  /emails/received/:id/reply` (round 2), `POST /emails/received/:id/forward`
  (round 3) — all FULL-permission only, so the JS/Python/Go SDKs and MCP
  server package can call them too, not just the dashboard.
- `GET /api/t/o/[emailId]`, `GET /api/t/c/[emailId]` — HMAC-signed open
  pixel / click redirect, no auth (signature in query string).
- `POST /api/to-html` — body `{ templateId, variables }` -> `{ html }`.
- `ALL /api/trpc/[trpc]` — see tRPC routers below.
- `POST /api/unsubscribe-oneclick` — RFC 8058 one-click unsubscribe, no auth
  (signed token in body).
- `ALL /api/v1/[[...route]]` — own REST API (campaigns/contacts/domains/
  emails), API-key bearer auth.
- `POST /api/webhook/dodo` — Dodo signature-verified billing webhook.

### tRPC routers (apps/web/src/server/api/routers), all `teamProcedure` unless noted

- `received-email` (`receivedEmailRouter`):
  - `list({ limit, after?, before? })` -> `{ data: ResendReceivedEmail[], has_more }`.
  - `get({ id })` -> `ResendReceivedEmail | null`.
  - `reply({ id, from, to?, cc?, text?, html? })` -> `{ id }`. **New this
    session.** Auth: team session, `id` scoped to `ctx.team.id`. Validates
    `from` is a verified sender on the team's domain inside `sendEmail`
    (`validateDomainFromEmail`); throws `BAD_REQUEST` if not, or if neither
    `text` nor `html` given; `NOT_FOUND` if the received email isn't on this
    team. Builds `In-Reply-To`/`References` from the original
    `ReceivedEmail.messageId`; defaults `to` to the original sender's bare
    address and `from` is left to the caller (UI defaults it to the
    original `to[0]`, i.e. the address the mail arrived at).
  - `setReceiving({ domainId, enabled })` -> toggles `Domain.receivingEnabled`.
- `email`, `template`, `campaign`, `contacts`, `domain`, `webhook`,
  `suppression`, `team`, `billing`, `admin`, `admin-review`, `waitlist`,
  `feedback`, `invitiation`, `audit`, `mfa`, `limits`, `dashboard`, `api` —
  existing, unchanged this session.

## Features

- Inbound receiving (existing): SMTP server (`apps/smtp-server`) accepts MX
  traffic on domains with `receivingEnabled`, parses with `mailparser`,
  uploads attachments to OCI Object Storage, POSTs to
  `/api/internal/inbound`, which persists `ReceivedEmail` + fires
  `email.received` webhook. Data: `ReceivedEmail`, `ReceivedEmailAttachment`,
  `Domain.receivingEnabled`.
- **Threaded reply (this session + round 2)**: dashboard `/receiving` detail
  view can send a real outbound reply to a received email, reusing the
  existing send pipeline (`sendEmail`: suppression check, content screening,
  domain verification, queue/provider dispatch) so quota/screening/
  suppression rules apply identically to replies and regular sends. Depends
  on: `email-service.ts:sendEmail`, `domain-service.ts:validateDomainFromEmail`,
  provider layer (`oci`/`smtp`) already forwarding `headers` through.
  **Round 2 additions**: `apps/smtp-server/src/inbound/server.ts` now calls
  `extractForwardedHeaders(parsed.headerLines)` (reused from the outbound
  submission proxy's `email-headers.ts`) and passes the result as `headers`
  to `postInboundMail`, so the original message's own `References`/
  `In-Reply-To` headers are captured on `ReceivedEmail.headers` (no
  migration — already `Json?`). `received-email-service.ts`'s
  `replyToReceivedEmail` now has `buildReferencesChain()`, which appends the
  current message's own Message-ID onto any prior `References` chain
  captured on inbound, so replying to a message that is itself a
  reply-of-a-reply threads correctly beyond one hop (RFC 5322 §3.6.4), not
  just one level deep as before. Also added this round: `POST
  /emails/received/:id/reply` on the public Resend-compat API
  (`resend/received.ts`, FULL-permission only, same `UnsendApiError` →
  `ResendApiError` mapping as every other route) and an MCP tool
  `reply_to_received_email` (`packages/mcp-server/src/tools.ts`) wired to
  it — so external SDK callers and AI agents can reply, not just the
  dashboard.
- **Forward (round 3)**: `received-email-service.ts`'s `forwardReceivedEmail`
  forwards a received email to a new recipient with a Gmail-style quoted
  header block + optional comment, reusing the original attachments by
  reading their bytes straight from inbound storage (new
  `getStorageObjectBytes()` in `inbound-storage-service.ts`, OCI `getObject`
  or local-disk fallback) and base64-encoding them for the outbound
  `sendEmail` pipeline — one read per attachment, no re-upload, no copy
  left behind anywhere. Exposed on all three surfaces: dashboard
  (`receivedEmail.forward` tRPC + `ForwardComposer` UI), public API (`POST
  /emails/received/:id/forward`), and MCP (`forward_received_email`).
  Gaps still open: no "replied"/"forwarded" badge in the list (needs a
  schema field — not added, no migration run per standing rule), no
  rich-text compose on the dashboard reply/forward boxes.
- Outbound send, campaigns, contacts/double-opt-in, templates, webhooks,
  suppressions, tracking, auth, billing, admin console, SDKs, own MCP
  server package — existing, unchanged this session; see audit for detail.
