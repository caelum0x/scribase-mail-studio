## Round 2 (2026-10-24)

Picked the top-ranked, not-yet-done item from `PLAN-2026-10-23-DEEP.md`'s "Next build
priorities" list: multi-hop reply threading plus exposing reply on the two surfaces that
weren't dashboard-only yet (public API, MCP/AI agents). All three were real gaps, not
already-shipped backlog noise — verified by reading the code before building, per standing
practice.

**1. Multi-hop inbound reply threading** (`apps/smtp-server/src/inbound/server.ts`,
   `apps/web/src/server/service/received-email-service.ts`)
   - The inbound MX server parsed `parsed.messageId` but silently dropped every other header,
     so `replyToReceivedEmail` could only ever build a one-link `References` chain (`<this
     message's id>`), not the real RFC 5322 §3.6.4 chain. A reply to a reply-of-a-reply broke
     threading in the recipient's mail client on the second hop.
   - Fix: `extractForwardedHeaders(parsed.headerLines)` (already written for the outbound
     submission proxy, reused as-is) now runs in the inbound path too and is passed as
     `headers` to `postInboundMail` → `persistReceivedEmail`, landing on
     `ReceivedEmail.headers` (pre-existing `Json?` column — no migration).
   - New `buildReferencesChain()` in `received-email-service.ts` reads the original message's
     captured `headers.references` and appends its own Message-ID (dedup'd) before sending.
   - No schema change. Verified: `apps/smtp-server`'s `pnpm build` (tsup, strict) and `pnpm
     test` (14 tests incl. `email-headers.unit.test.ts`) both clean; `apps/web`'s `pnpm
     typecheck` clean; targeted vitest run of `received-email-service.unit.test.ts` (7 tests)
     and `received.api.test.ts` (6 tests) both still pass unmodified.

**2. `POST /emails/received/:id/reply` on the public Resend-compat API**
   (`apps/web/src/server/public-api/resend/received.ts`)
   - Scribase Mail Studio extension beyond Resend's own surface (Resend has no inbound mail
     at all). FULL-permission only — falls out of the existing `checkApiKeyAccess` policy
     automatically since it isn't in `SENDING_ROUTES`, matching the file's own doc comment
     ("All endpoints require FULL permission").
   - Thin wrapper over the same `replyToReceivedEmail` service the dashboard tRPC procedure
     already calls, so quota/screening/suppression/threading behavior is identical across
     both surfaces — no duplicated business logic.

**3. MCP tool `reply_to_received_email`** (`packages/mcp-server/src/tools.ts`)
   - Calls the new REST endpoint via the existing `ScribaseMailClient.post`. Lets an AI agent
     (Claude, etc.) connected to the Scribase Mail MCP server reply to an inbound email
     directly, completing the `list_received_emails` → `get_received_email` →
     `reply_to_received_email` loop that was previously read-only.
   - Verified: `packages/mcp-server`'s `pnpm typecheck` and `pnpm test` (11 tests) both clean.
